# 设备本地持久诊断

设备保存有容量上限的数值事件日志，用于间歇性 BLE 与录音故障。记录录音请求、
去抖后的按键边沿与动作、主机状态、连接变化、麦克风和发送错误，以及录音结束来源，
以便区分“未按第二次却提前结束”的触发方。本地入队成功不等于电脑已收到。
不保存 PCM、转写、任意主机文本或设备身份；主机消息只保留类别位、字节数和哈希。

## 存储与时序

新增 `diag_log` 数据分区，子类型 `0x40`，地址 `0x310000`，大小 `0x40000`
（256 KiB），位于原有 3 MiB 应用之后、受保护的 `cardid` 之前。
`cardid`、Recovery、NVS、引脚和 BLE V1 格式保持不变。需要配套更新分区表；
仅给旧分区表刷入应用时，本地诊断会停用。

首个 4096 字节扇区保存不可变的 64 字节格式头，其余 63 个扇区保存 4032 条
64 字节记录。写满时回收最旧扇区，保留量以事件数计算，不保证固定天数。
合并固件仅包含格式头，不含运行日志；分段升级只写格式头扇区，保留全部日志数据扇区。
首次配置必须先备份新划定区域：旧分区表未分配的字节也可能含历史固件残留。
不得擦除整个 Flash 或任何受保护区域。

调用方通过 192 条（12 KiB）容量的 RAM 队列立即入队，不等待写盘；低优先级任务负责持久化。
队列溢出由 `queue_dropped` 显式计数。音频统计每十秒及会话结束记录一次，包括
首帧延迟、最长读取时间、发送耗时、帧间停顿、堆和栈余量。
重试详情最多每五秒一条；连续十五分钟没有其他事件时写入心跳。
原有每秒音频串口 INFO 统计降为 DEBUG，减少录音时的控制台负担。

音频工作任务与日志任务之间的门控，防止该任务采集或播放期间进行任何日志读取、
编程或擦除；已经进行的一次追加操作可能在新音频流开始前完成。待写日志暂留有界
RAM 队列，音频暂停后再落盘，并保留事件时间戳与顺序。因此长录音过程中突然断电，
可能丢失该轮尚未写入的诊断事件。队列容量和限流覆盖普通五分钟录音，异常事件突发
仍可能溢出，会显式计数。

先写数据与 CRC，最后单独写提交字。启动时扫描已提交且 CRC 正确的记录，跳过撕裂
记录并继续序号；运行期间从不擦除格式头。格式头未知或损坏、I/O 失败时停用写入，
不自动格式化，也不阻塞正常 BLE 功能。突然断电可能丢失尚在 RAM 的最新事件；
这不是 panic 或 core dump 收集器。

## 读取日志

录音与提交空闲后接上 USB。ROM 读取会短暂复位蓝牙，随后重启应用，不擦除或写入
Flash。`read` 命令需要所选 Python 环境安装 esptool 5.6.0；离线解码只用标准库。

```text
python tools/device_diagnostics.py read --port COM17 --output device-log.bin
python tools/device_diagnostics.py decode device-log.bin --output device-log.json
```

读取工具核对诊断分区范围，拒绝覆盖已有采集文件，仅导出日志区。`boot_id` 与启动后
毫秒数关联同一轮启动；它们不是日历时间。解码器按序号恢复顺序，包括序号回绕，并
统计损坏或未提交的记录数。

## V1 二进制格式与事件含义

整数均为小端。格式头由 `VDJ1`、uint16 版本与记录大小、uint32 扇区与分区大小、
十一个保留 uint32 字以及前 60 字节的 IEEE CRC32 组成。记录由 `VDR1`、
uint16 版本与事件号、uint32 序号/启动 ID/启动毫秒/会话、八个参数字、前 56 字节
CRC32 及 `CMIT` 提交字组成。布局断言和主机测试保护边界。
事件号在 `main/device_diag.h` 声明，由 `tools/device_diagnostics.py` 解码；
新事件追加编号，不得重新编号。

| 事件 | 主要线索 |
| --- | --- |
| `button`、`start_requested`、`stop_requested` | 去抖 PRESS/RELEASE/LONG、识别动作、时长、状态位、连接代号；区分第二次 UP 松手与主机触发停止 |
| `host_state` | 应用状态前的 ready/recording/processing/success/error、设备标志、入队帧数，以及可选消息类别与哈希 |
| `capture_stopped`、`capture_aborted` | 原因、帧数、重试、连接与会话上下文；正常结束额外记录控制消息入队结果 |
| `audio_stats`、`first_frame` | 最长停顿/耗时、首帧延迟；入队成功仍不是主机收据 |
| `tx_failure`、`tx_retry`、`microphone_error` | 准确数值返回码、尝试次数、等待或读取时长、发生阶段 |
| `connect`、`disconnect`、`mtu`、`subscribe`、`link` | 连接结果/断连原因、真实间隔与 MTU、订阅与连接代号 |
| `tx_resources` | 阶段 1 为 mbuf 分配失败、2 为通知协议栈拒绝、0 为摘要；当前/最低 MSYS 空闲块、累计分配/协议栈失败次数、帧数和连接代号 |
| `msys_pools` | 分别记录 MSYS 1/2 当前空闲、启动以来最低空闲、总块数和每块字节数；未发现的池解码为 null，而不是零 |
| `start_blocked`、`end_delivery` | 上轮结果未结束时的再次按键；提交或错误通知、返回码及同一连接的断开兜底 |
| `boot`、`build`、`queue_dropped`、`storage_slow` | 复位原因、ELF 哈希、RAM 丢弃量及异常慢的存储操作 |

状态位：bit 0 录音、1 请求停止、2 主机就绪、3 控制订阅、4 音频订阅、5 等待主机结果、6 发送结束事件。
按键/边沿/动作枚举遵循 `bsp_button.h` 与 `button_gesture.h`；停止原因单独命名解码，
不改变按键语义。失败录音通过工作任务有界重试发送带会话的 `device_error`，不再发送普通 `ptt_up`。
如果结束事件仍无法入队，则请求断开同一连接/会话，不会断开后来替换的新连接。
正常结束发送 `ptt_up` 后，等待主机 success/error/ready，才接受下一次 UP 开始。
处理中按键会显示 "Wait for result"，不会排队自动启动。主机明确报错仍会停止录音。
BLE V1 包格式保持不变，不延长主机看门狗，也不把本地入队成功当作主机已收到。
音频重试仍保留 80ms 上限，以便观察真实吞吐变化，不通过延长超时掩盖拥塞。

运行 `./tools/validate.sh` 验证可移植日志断写/回绕、解码器、固件构建和格式头/保护区
约束。跨复位导出、带日志录音、长会话、压力下回绕与溢出、突然断电及电池影响需分别
进行真机验收。

## 音频缓冲所有权

音频负载明确请求配置中的大 MSYS 池，并预留 16 字节头部空间；
NimBLE 仍会从小池另行分配 ATT 命令头，与控制和接收共用，并非硬性保留控制缓冲。ESP-IDF 5.5.3 的 `ble_hs_mbuf_from_flat()` 请求零大小包头，
选择最小可用尺寸池，池耗尽时不会尝试下一池。所有音频都使用该接口，会在大池
24 块全部闲置时仍返回 ENOMEM。保留默认 12 x 256 字节及 24 x 320 字节的总预算，
固件校验会核对配置；本次不增加缓冲数量或音频重试时限。
交给 NimBLE 前检查容量并在追加失败时释放 mbuf。主机测试复现小池耗尽而大池
仍有 24 块的场景，并验证音频池耗尽时控制池仍保留容量。

设备现在明确请求固定 15ms 连接间隔，取代原来的 15～30ms 范围。此前 Windows
在允许范围内选择了 30ms，在每 20ms 产生一帧语音时通知资源耗尽。同一固件仅临时
改用 Windows 的 15ms 偏好后，连续短录音中观测到的失败和重试消失。
固定请求避免明确允许主机选用 30ms，但最终参数仍由中心设备决定。应检查真实 `link`
记录，并在每种主机上重复长录音测试；分池和参数请求均不保证所有适配器的吞吐。
音频重试上限、缓冲数量与 BLE V1 数据包保持不变。
